# 提交规则

提交信息用中文写，格式参考 [Conventional Commits](https://www.conventionalcommits.org/zh-hans/v1.0.0/)。推送到 `main` 时 CI 会检查，不合格就和 `gofmt` 没过一样，不打标签、不发版；本地可以装钩子，提交时就拦下来。

## 格式

```text
<type>(<scope>): <标题>

<正文，可选>
```

例：

```text
feat(chat): 国内版对话入口出错时切备用入口

照官方桌面端 5.8.3 的失败切换：主入口出错切备用入口 wb.tencentbuddy.com，
每个请求最多切一次；DNS 失败与 408/502/503、传输错误按规则换 HTTPDNS 候选 IP；
按入口记熔断器（60 秒内 3 次打开，退避逐次延长）。国际版与自配中转不受影响。
```

## type

| type | 用在 |
|---|---|
| `feat` | 新功能，或使用者看得到的行为变化（包括出站请求改形状） |
| `fix` | 修正错误行为 |
| `refactor` | 行为不变的重构、删掉不用的代码 |
| `perf` | 性能 |
| `test` | 只改测试 |
| `docs` | 只改文档 |
| `build` | 构建方式、依赖、前端构建配置 |
| `ci` | GitHub Actions 工作流、检查脚本 |
| `chore` | 发版、同步上游、其他杂务 |
| `revert` | 撤回之前的提交，标题写被撤回提交的标题，正文写原提交的 SHA 和原因 |

## scope

必填，按功能从下表选，不按目录选：同一个功能的代码常常跨 `internal/upstream`、`internal/panel` 和 `web/`。一个提交涉及几个 scope 时选主要的那个；分不出主次，多半说明该拆成几个提交。

| scope | 范围 |
|---|---|
| `chat` | 对话转发：请求体、对话请求头、会话 id、提示词改写、对话入口失败切换 |
| `models` | 模型目录、`/v1/models`、档位与倍率 |
| `auth` | 凭证文件、刷新令牌、身份字段 |
| `login` | 添加账号：面板登录、命令行登录、国际版注册 |
| `credit` | 积分余额、签到、补偿、礼包、试用 |
| `tasks` | 任务中心、成长体系、旅行、桌面端 / 网页 / 小程序事件上报 |
| `pool` | 账号池与选号 |
| `session` | 会话粘性与会话分配 |
| `net` | 出站公共层：域名、框架请求头、UA、压缩、HTTPDNS、网页登录态 |
| `panel` | Web 管理面板（`web/` 与面板接口） |
| `server` | 入站服务：路由、鉴权、停机、请求日志与指标 |
| `config` | 配置项、默认值、环境变量 |
| `docker` | 镜像与 Compose |
| `release` | 版本号、更新日志、发版流程、一键更新 |
| `upstream` | 只用于同步上游，见[下文](#同步上游与发版) |
| `repo` | 仓库本身：README、许可证、提交规则与钩子 |

## 标题

- 不超过 50 个字（中英文、数字、标点都算一个），末尾不加句号。
- 写做了什么，让人不看代码也知道改了哪里、有什么效果；不写文件名、函数名。
- 版本号只出现在 `chore(release): x.y.z` 里。官方客户端的版本、实测日期这类依据写进正文。

## 正文

改动不一目了然时必须写正文，和标题之间空一行：

- **为什么改**：原来哪里不对，或者要对齐什么。
- **依据**：对照的官方安装包版本、抓包或实测的日期与结果。
- **没确认的**：哪些地方没实测、靠推断，写明「未确认」。

用自然段或 `- ` 列表都行，不用硬折行。

## 一个提交放多少

- 一个提交是一个完整的功能或修正，连同它的测试和文档一起提交；不为凑数硬切，也不把不相干的改动塞进一个提交。
- 每个提交都要能编译、测试通过（`go build ./...`、`go test ./...`，改了前端再跑 `npm run build`）。
- 使用者看得到的改动，`appVersion` 和 `docs/CHANGELOG.md` 放在最后的发版提交里一起改，见[发版与版本号](releasing.md)。

## 同步上游与发版

- 同步上游的合并提交写 `chore(upstream): 同步上游 <上游短 SHA>`，正文列上游这次的主要改动，和[同步记录](upstream.md#同步记录)一致。合并步骤见[项目来源与上游同步](upstream.md)。
- 发版提交写 `chore(release): x.y.z`，只改 `appVersion` 和更新日志。

## 签名

- 所有提交都要签名，GitHub 上显示 Verified。
- 不加 `Co-authored-by` 等署名。

## 自动检查

两处用的是同一个脚本 `scripts/commit-msg.sh`，查的内容一样：格式、type 与 scope 在上面的列表里、标题字数与句号、版本号与同步上游的写法、标题和正文之间空行、没有 `Co-authored-by`。

**CI**：go-binaries 工作流的 `commits` 任务检查这次推送新增的提交。只沿 `main` 的第一父提交查，合并进来的上游提交不查；强推后推送前的提交已不在历史里，就查最近一个版本标签之后的提交。没过时 `test` 不跑，后面的构建、镜像和 Release 都不发。

**本地钩子**：每个 clone 启用一次，之后 `git commit`、`git merge` 写的提交信息不合格会被拦下，原消息留在 `.git/COMMIT_EDITMSG`：

```bash
git config core.hooksPath .githooks
```

本地 `git rebase --autosquash` 用的 `fixup!`、`squash!`、`amend!` 临时提交钩子放行，推送前要压掉，CI 不放行。要检查已有的提交，可以直接跑：

```bash
scripts/commit-msg.sh --commits origin/main..HEAD
```
