## Docker 部署登录后报「写入 auths/… 失败: permission denied」

容器默认以 uid 10001 运行，而宿主机上挂载的 `auths/`、`data/` 属于你自己，容器写不进去。任选一种解法：

```bash
# 方案 1（推荐）：让容器以你自己的身份运行
docker run --user "$(id -u):$(id -g)" ...
# Compose：
PUID=$(id -u) PGID=$(id -g) docker compose up -d --force-recreate

# 方案 2：把目录交给容器默认用户（需要 sudo）
sudo chown -R 10001:10001 ./auths ./data ./config.json

# 方案 3：以 root 运行（NAS 不方便 chown 时用，自担风险）
docker run --user 0:0 ...
```

## 容器一直显示 unhealthy

镜像的健康检查访问 `/healthz`，而没有可用账号时它返回 503。添加账号后会自动变成 healthy。

## 忘了 api_key

打开配置文件看 `api_key` 字段（Docker 快速开始的配置在 `data/config.json`）。首次自动生成时，启动日志里也打印过一次。

## 429 code=6004 是什么

这是**某个模型**的用量超限，不是账号整体被限流。上游的提示通常带「将在 YYYY-MM-DD HH:MM:SS 重置」：

- 网关把该账号的冷却时间设到上游给的重置时刻（封顶 `cooldown.soft_rate_max`，默认 2 小时）；
- 同一个账号**换别的模型**照样可用；
- 面板「账号池 → 模型锁池」能看到哪些模型被限、还剩几个号、多久解锁。

## 429 code=14003「模型繁忙」是什么

上游说这个模型此刻请求量饱和，几秒到几十秒就会过去（官方客户端遇到它会原样重发，最多等 32 秒）。国际版的 deepseek 常见。

- 网关当场换号重试，只把这个号的这个模型冷却约 30 秒，这个号的别的模型照常可用；
- 所有号的这个模型都在冷却时，网关回 429 并带 `Retry-After`（几十秒），客户端稍等重试即可；
- 号少的域（比如只有两三个国际版号）可能一时全在冷却：`pool.cross_realm` 设成合池（`merge`）或国内版优先（`cn_first`）时，不带前缀的请求会回落到另一个域，带 `global:` 前缀的请求会暂时报错（429 或 503），稍等再试。

## 503「all accounts are busy」是什么

能接这个请求的号都健康，只是在途请求都满了（国内版每个号默认 3 个、国际版 2 个，见 `pool.max_in_flight`、`pool.max_in_flight_global`），或者设了每号每分钟请求数 / Token 数上限（`pool.max_rpm`、`pool.max_rpm_global`、`pool.max_tpm`、`pool.max_tpm_global`）并且到了上限。网关先让请求排队，等有号放出名额再转发，最多等 `pool.in_flight_wait`（默认 30 秒）；等满还没有空位才回这个 503。有号是因为每分钟请求数到上限时，错误信息里写的是 `requests-per-minute`，`gateway_hint` 以 `rpm_full` 开头；是 Token 数到上限时写的是 `tokens-per-minute`，hint 以 `tpm_full` 开头。

- 偶尔出现：并发的高峰，稍等重试即可；
- 经常出现：同时发的请求比号能接的多，加号，或者调大在途上限（国际版风控更紧，调大前先小幅试）；`rpm_full` 时调大每分钟请求数上限；
- 排队期间客户端收不到任何数据，流式请求的首字会晚到，客户端的超时要比排队上限长。

## 503「no account in this API key's groups」是什么

用的客户端密钥在面板「密钥」里勾了账号分组，这个请求只能用这些组里的号，而组里的号此刻都接不了（冷却、禁用、暂停、这个模型冷却或被屏蔽、积分保底拦着），网关不借组外的号。在面板账号池按分组筛出来看这些号的状态，或者往组里加号；不想限了就在密钥里把分组都去掉。见[网关与选号 · 选号策略](gateway.md#选号策略)。

## 请求被上游内容审核拦截

Claude Code、Codex 等客户端的系统提示词里有固定模板句，可能被上游审核误拦：

- 默认 `prompt.mode=passthrough`：遇到拦截，网关会在同一请求内换成中性提示词自动重试一次，当天后续请求直接用中性提示词。
- 仍频繁被拦时，改成 `custom`（用网关自带提示词替换）或 `append`（在客户端提示词后追加）。
- 如果换了提示词仍被拦，说明是对话内容本身触发了审核。

详见[网关与选号 · 系统提示词与内容审核](gateway.md#系统提示词与内容审核)。

## 流式回复中途断掉，或非流式报 504 `upstream_idle`

上游连着、也还在发保活帧，但 `upstream.idle_timeout_seconds`（默认 300 秒）内没有一帧正文：网关的空闲看门狗会掐掉这条流，把名额放回号池。流式请求的 HTTP 头早已是 200，客户端看到的是流中断；非流式回 504，`error.code` 是 `upstream_idle`。只有**内容帧**续命——SSE 注释行、`{"type":"ping"}` 这类心跳帧不算，否则保活帧会把计时器一直刷新、空闲上限等于没有。

对照检查：网关日志 `WARN: [server] stream … upstream stalled, no content frame within idle window`；请求记录里这一跳是错误（不是「客户端断连」的成功记账）。偶发就是上游那一刻卡住，重试即可；频繁出现说明该模型/号确实吐不出字，`idle_timeout_seconds` 调大只是让等待更久。

## 大上下文请求报 read body: i/o timeout

入站请求体上传超过了 `server.read_timeout`（默认 300 秒），常见于经过多层反代转发的大请求。调大这个值（`0` = 不限制）后重启。网关本身不限制请求体大小。

## 账号被禁用了怎么恢复

- session 连续 3 次失效会被自动禁用，原因写在面板账号状态与 `/status` 的 `disabled_reason` 里。
- 面板账号行点「解冻」可以直接复活；token 确实失效的，用「添加账号」重新登录同一个账号覆盖凭证。

## 签到汇总里的「失败 N」是什么，怎么查

「失败」只说明这一轮签到调用没成功，**不代表号有问题**：签到失败不罚号（不进冷却、不禁用、不影响选号），同一个号紧接着照样查余额。号没过期、没被限流却出现在失败里，多半是下面几种情况之一，按汇总行的「失败明细」或 `checkin <号>: <错误原文>` 那行对：

| 错误原文里出现 | 含义 | 怎么办 |
|---|---|---|
| `签到活动未开启` | 上游当期没有签到活动（签到状态接口回 `active=false`，如活动到期未续），号完全正常 | 等官方开活动，不用处理 |
| `已签到` | 上游幂等拒绝 | 正常应记成「已签到」；若被记成失败，说明文案没被识别，可以提 issue 补关键词 |
| `http 401` / `403` | 凭证失效 | 用「添加账号」重新登录同一个号覆盖凭证 |
| `http 5xx`、`timeout`、`EOF`、`tls` | 网络或上游抖动（已自动补打 2 次，间隔 2s、4s） | 看代理与出口，通常下一轮自愈 |
| `http 429` / `Too Many Requests` | 上游软限流：同一个出口短时间内连着打维护接口（签到、保活、查余额都会中），排在前面的号最容易吃 | 已改为让号之间错开 1.5 秒、429 等 20 秒补打一次；持续出现说明出口被上游盯上，考虑给号分代理 |
| `请求被拦截` / `11128` | 渠道指纹被上游判定不像官方客户端 | 见[出站请求对齐](upstream.md)，别反复重试 |
| 其它业务码（如 `10001`） | 上游业务拒绝 | 按文案判断；企业号与 global 号本来就不签到（汇总里记「跳过」） |

**失败了今天还会再签吗？** 会。签到按 `schedule.checkin_hours` 跑（默认 `[9, 21]`，一天两轮），9 点那轮失败的号，21 点会重新签一次——已经签上的号那时返回「今天已签到」被记成幂等成功，不会重复扣次数。所以一次失败不等于当天漏签；但如果两轮都失败（比如出口整点一直被限流），当天就真没签上，只能看第二天的汇总行确认。

**日志怎么看**：每轮末尾有一行汇总，失败的号和跳过的号都带 `昵称(uid8)` 与错误原文，例如：

```
checkin 汇总：成功 2 / 已签到 3 / 失败 1 / 跳过 1；失败明细 193****7419(1f2ec734)：upstream soft_rate (http 429): {"error_msg":"Too Many Requests"}；跳过明细 xi***@gmail.com(2168905e)：国际版（global）无签到体系
```

保活（`keepalive 汇总`）同样有成功/失败/跳过三档与明细。

## 多个账号共用一个 IP，怎么一次只用一个

在面板里对暂时不用的账号点「**暂停选号**」：它们不再接请求，但签到、保活、余额刷新、成长任务照常进行。需要时点「恢复选号」立即回池。详见[禁用、暂停与企业版账号](tasks.md#禁用暂停与企业版账号)。

想让号各走各的 IP，用面板「代理」页的代理池：号绑在池上，各分一个代理，池里还能限每个代理最多几个号，见[按号代理与代理池](proxy.md)。

## 官网积分记录的「使用端」显示什么

官网按出站请求的 User-Agent 归因。默认 UA 按账号所在域对齐官方桌面端：国内版 `WorkBuddy/5.11.3 WorkBuddy/5.11.3 CLI/2.176.0`，国际版 `WorkBuddy/5.11.7 workbuddy-ai/5.11.7 CLI/2.176.0`；需要时可用 `upstream.user_agent` 整体覆盖，或用 `upstream.client_version` / `upstream.cli_version` 只改版本号。改完需要重启。

## 每天早上的积分到期日报没收到

日报走的是「告警」通道（`notify.format`，默认 Bark），所以三处都要开着：`notify.enabled=true` 且 `notify.url` 填好（Bark 是 `https://api.day.app/<device_key>`）、`schedule.report_enabled=true`、`schedule.report_hours` 落在一个整点上（默认 `[8]`，按进程时区；Docker 里记得 `TZ=Asia/Shanghai`）。想知道是通道问题还是时点问题，直接 `curl -X POST -H "Authorization: Bearer <面板密钥>" http://<面板地址>/panel/api/notify/report`：能收到，说明通道没问题、只是还没到点；回 501 说明通道或调度器没起来；回 502 附带的是通道真实错误。正文首行是余额快照时刻——如果它离现在很远，把 `schedule.balance_refresh_enabled` 打开。
